# Architecture

One product, one command. `docker compose up` brings up a seeded, working portal on localhost
with the network off. No cloud account, no hosted database, no external API, no auth as a
service. A judge runs it, the acceptance checker hits it over HTTP with seeded tokens. A
standalone verifier can recompute any published result. Everything below serves those facts.

## Stack and why

- Django plus Django REST Framework. Batteries we would otherwise hand-roll: authentication and
  sessions, a real role model, an ORM with migrations, an admin and CSV in a few lines. DRF gives
  a documented REST API and an OpenAPI schema close to free, which is the API-first gap no
  incumbent fills.
- SQLite. It is Django's default, so the portal is a single container. Nothing to pull at boot,
  no database-ready race. The whole state is one file an organizer can copy or delete. The
  schema stays Postgres-compatible, so a production deployment swaps the connection string.
- `cryptography` for Ed25519, used only to sign and verify results bundles.

## Components

    docker compose up
       -> app container: Django + DRF (gunicorn)
       -> entrypoint: migrate, then seed (loads fixtures, prints per-role tokens), then serve
       -> SQLite file in a mounted volume, plus the Ed25519 signing key generated on first boot
       -> GET /health returns 200 only once migrated and seeded

    external clients (no login):
       run.py           attaches a seeded token per role, makes the 7 acceptance requests
       verify.py        recomputes a published ranking, checks the hash and the signature

## Authentication and role isolation

The checker never logs in, so the seed creates one user per role (organizer, two judges,
participant) with fixed deterministic tokens and prints the exact header lines on boot. These are
seed and development tokens, stated plainly as such in the README and the logs. They exist so
an offline checker can attach without a login step. A real deployment issues normal tokens.

Role isolation is enforced in the backend, never in a template. A judge reading scores gets only
their own, derived from the authenticated identity. The endpoint that can name a specific judge
honors that only when the caller is that judge or an organizer, so a second judge asking for a
peer's scores is refused with 403. A participant on a judge route is refused. These are DRF
permission checks on the view, so a curl with the wrong role fails exactly as a browser would. A
judge is also scoped to their assigned tracks through the `judge_tracks` relation.

## Request lifecycle

- A judge scores a project: POST creates a `Score` and its per-criterion `ScoreValue` rows, guarded
  by the judge-and-assignment check, then writes an `AuditLog` entry.
- Publishing results: a publish action reads the live scores through an adapter into
  `(judge, canonical_project, composite)` triples, runs the judging engine, builds a payload of
  {raw scores, rubric and weights, method and params, code commit, ranking}, signs it with the
  deployment key, stores the `Bundle` and logs the publish. The public key is served at
  `/api/verification-key` and the bundle at `/api/results/bundle`.

## Judging pipeline

The engine is pure Python and never imports Django, so it is unit-tested in isolation and reused by
`verify.py`. Weighted composite first, then the additive judge-bias plus empirical-Bayes shrinkage
ranking, with a guarded z-score cross-check and an optional Bradley-Terry pairwise mode. The math
and its defense are in JUDGING.md.

## Reproducible signed results

The signing key is generated by the deployment on first boot and kept in the deployment's own
volume. It is never a personal or shared key, because the product is meant to be forked and
self-hosted. `code_commit` is baked into the image as `GIT_COMMIT` at build time, so a bundle names
the exact code that produced it. `verify.py` needs only the standard library plus `cryptography`,
recomputes the ranking from the raw scores in the bundle and checks the digest and the signature.
This is how a result is trusted without trusting the host.

## Offline, one command, adoptable

The image bundles the fixtures and every asset, so nothing is fetched at runtime. The entrypoint
migrates then seeds then serves, the health endpoint flips to 200 only when the portal is ready,
and the seed logs the counts it created and the per-role headers. A second `up` does not duplicate
data. Reset is a volume removal.

## Trade-offs and non-goals

- SQLite over Postgres in development is a deliberate choice for a clean offline boot. The schema
  and migrations stay portable so production is a connection-string change.
- Seeded fixed tokens are a development convenience for the offline checker, not a production auth
  posture, which the docs state.
- The engine favors a defensible, documented method over a black box. Where two methods disagree we
  publish both rather than hide the disagreement.
