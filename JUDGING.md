# How judging works

This platform turns judge reviews into a ranking that stays fair when judges see
different projects, when some projects get more reviews than others and when a judge
scores everyone the same. Every published number is reproducible. The results bundle
carries the raw scores, the method and a signature, so anyone can recompute the ranking
and check it with `verify.py` without trusting the host.

The numbers below come from running the method on the event fixture: 126 reviews from 30
judges over 41 submissions, which merge to 40 projects once the duplicate is resolved.

## 1. From a review to a project score

Each review scores every rubric criterion from 1 to 5. The organizer sets a weight per
criterion. We combine them into one composite per review with a weighted mean:

    composite = sum(weight_c * score_c) / sum(weight_c)

A weighted mean keeps the 1 to 5 scale, so adding a criterion or changing a weight does
not distort the range and a review that skips a criterion is averaged over the criteria it
has. The market leader cannot weight criteria at all, so this is deliberate.

## 2. Removing judge bias

Judges run generous or strict. We fit an additive model over every review:

    composite(project i, judge j) = mu + project_quality_i + judge_bias_j + noise

We estimate each `judge_bias_j` and subtract it, so a project is measured on its quality
rather than on which judges it drew. A judge who scored every project the same contributes
only a bias offset and no ranking signal, which is correct, because identical scores say
nothing about which project is better. We never divide by a judge's score spread, so a
zero-variance judge is not a failure case and needs no special branch.

## 3. Combining reviews fairly across uneven coverage

Coverage on this fixture runs from 2 to 5 reviews per project. Two mistakes to avoid:

- We average across judges, never sum. Summing would reward a project for being reviewed
  more, which is a coverage artifact and not quality.
- A 2-review average is noisy, so we shrink each project's quality toward the overall mean
  by an amount that grows with its review count:

      final_i = mu + B_i * (bias-adjusted mean quality of project i)
      B_i     = n_i / (n_i + k)

  On this fixture `k = 0.81`, fit from the data as the residual variance over the
  between-project variance. A 2-review project keeps about 71 percent of its own signal, a
  5-review project about 86 percent, so coverage buys confidence rather than rank. We report
  every score with an uncertainty band and its review count. Projects whose bands overlap are
  a statistical tie and go to a tie-break, not to a decision on the third decimal. This is the
  shrinkage result of Efron and Morris (1975).

## 4. The awkward cases

- The duplicate submission (two records for the same team, title and repo) is merged to one
  canonical project before scoring, so it is neither ranked twice nor split.
- Unfinished review batches are left as missing data. We never impute a score. Missing data
  lowers a project's confidence, it does not invent a number.
- Zero-variance and very-low-coverage judges are handled by the model above. In the z-score
  cross-check they are mean-centered and never rescaled.

## 5. Pairwise mode

For close calls we also support Bradley-Terry pairwise ranking. Within each judge we turn
"scored project A above project B" into one win for A over B, which cancels that judge's
leniency because both projects passed the same judge. On the fixture this synthesizes 277
within-judge comparisons over the 40 projects. We fit strengths with the standard MM
iteration and add a virtual opponent to every project, the regularizer from the Crowd-BT
paper, so the estimate stays unique even where the comparison graph is sparse. Ranking is by
the fitted strength. Each strength carries a bootstrap standard error from resampling the
comparisons, so a reader sees which ranks are solid and which lean on only a few comparisons.

The pairwise and the weighted-rubric rankings agree on 7 of the top 10 projects and
disagree on the top seat, which is exactly the signal a pairwise pass is for. We publish both
and flag the disagreement rather than hiding it.

## 6. Reproducible signed results

When results are published the platform emits a bundle that contains the raw scores, the
rubric and its weights, the method and its fitted parameters and the code commit that
produced them, plus the ranking. The bundle is hashed with sha256 over a canonical encoding
and signed with an Ed25519 key. That key is generated by the deployment on first boot and
kept in the deployment's own volume, it is never a personal or shared key. The public key
travels inside the bundle and is served at `/api/verification-key`.

`verify.py` recomputes the ranking from the raw scores, confirms it matches the published
ranking, checks the digest and verifies the signature. It needs only the standard library
plus `cryptography` for the signature step. Tampering with a score or a rank fails the check.
This turns "we normalized the scores" into "here is the record, recompute it yourself".

## 7. Integrity and audit

Judges cannot read other judges' scores or the aggregate, enforced in the backend. Judges
cannot review their own project. Every raw review, the rubric version, every judge
assignment, the method version and constants and every fitted number are recorded so any
result is reproducible and every intervention (a merge, a flagged low-information judge, a
statistical tie) is visible. The audit is exportable as CSV or JSON so an organizer can check
it without a database client.

## 8. Method choices, stated plainly

- We weight the criteria first then normalize the composite. Per-criterion normalization
  needs more reviews per judge than this event has, so it would add noise.
- The primary method is the bias-removal-plus-shrinkage model above. As a cross-check we run
  a guarded per-judge z-score (mean-center, divide by a spread that is floored and that falls
  back to mean-centering for a flat or thin judge). The two agree on 6 of the top 10 projects
  on the fixture. Where they disagree we say so.
